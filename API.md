# API рамки

HTTP-API, який керує галереєю фоторамки та її слайдшоу.

Галерея тримає **і фото, і відео**. Фото висить нерухомо, відео крутиться по колу
доти, доки триває його слот, — тобто п'ятисекундний кліп у хвилинному слоті
програється дванадцять разів поспіль, а не завмирає на останньому кадрі. Вимоги
до відео жорсткі, бо декодує його GPU, а не процесор: див.
[«Яке відео рамка може показати»](#яке-відео-рамка-може-показати).

**База:** `http://<адреса-рамки>:5000` (у локальній мережі — `http://192.168.0.146:5000`)

---

## Автентифікація

Кожен запит має нести заголовок `Authorization` зі значенням `AUTHKEY` з `.env`.
Це **сирий ключ, без префікса** `Bearer`.

```
Authorization: <AUTHKEY>
```

| Ситуація | Код | Тіло |
|---|---|---|
| Заголовка немає | `401` | `{"error": "Authorization key is required"}` |
| Ключ не збігається | `401` | `{"error": "Forbidden"}` |

Помилки автентифікації — єдині, що повертають не-200 і не мають звичайної обгортки.

---

## Формат відповіді

Усі методи повертають однакову обгортку:

```json
{
  "success": true,
  "message": null,
  "data": {}
}
```

> **Важливо для клієнта.** Помилка рівня застосунку («фото не знайдено», «нема що
> завантажувати») теж приходить із **HTTP 200**, лише з `"success": false` і текстом у
> `message`. Перевіряти треба поле `success`, а не HTTP-код. При невдачі `data` — `[]`
> в усіх методах, окрім `upload-images`: там навіть у разі повної невдачі приходить
> `{"images": [], "rejected": [...]}`, бо причина відмови потрібна саме тоді.

Не-200 повертають тільки: `401` (автентифікація), `405` (невірний метод для роуту)
і `404` (невідомий шлях). Останні два віддають HTML Flask, а не JSON.

## `GET /api/v1/list-images`

Список галереї — фото й відео разом, **найновіші першими**, з мініатюрами у
вигляді data-URL.

### Параметри

| Параметр | Тип | Дефолт | Поведінка |
|---|---|---|---|
| `page` | int | `1` | Обрізається до діапазону `1…maxPage` |
| `prePage` | int | `5` | Обрізається до `1…60` |

Некоректні чи відсутні значення (`0`, `-5`, `abc`) мовчки замінюються дефолтними.
Запит `page=999` поверне останню наявну сторінку, а не порожній список.

### Відповідь

```json
{
  "success": true,
  "message": null,
  "data": {
    "images": [
      {
        "name": "1744960595611_IMG_1611.jpeg",
        "type": "image",
        "file": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQAAAQABAAD..."
      },
      {
        "name": "1788690163183_IMG_3400.mp4",
        "type": "video",
        "file": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQAAAQABAAD..."
      }
    ],
    "pagination": { "page": 1, "prePage": 5, "maxPage": 2, "total": 9 }
  }
}
```

`name` — ідентифікатор елемента; саме його передають у `delete-images`.

`type` — `image` або `video`. Поле **нове**. Клієнт, який його не читає, працює як
раніше: відео просто виглядатиме в галереї як звичайне фото.

`file` — готова до вставки в `<img src="...">` мініатюра **180×307** (пропорція
рамки). Для відео це кадр, знятий приблизно на першій секунді (не з нульової:
кліпи надто часто починаються з чорного кадру). Формат той самий, тож один `<img>`
малює і фото, і відео — окремого поля для постера немає.

### Про розмір відповіді

Мініатюри вбудовані в JSON у base64, тож відповідь важить приблизно **20 КБ на фото**:
близько 157 КБ при `prePage=60`. Рамка — одноядерний ARMv6, тому для галереї бери
`prePage` 10–20, а не 60.

```bash
curl -H "Authorization: $KEY" \
  "http://192.168.0.146:5000/api/v1/list-images?page=1&prePage=10"
```

## `POST /api/v1/upload-images`

Приймає фото **і відео**. Фото кадрує під рамку, відео перевіряє й лишає як є.

**Тіло:** `multipart/form-data`, поле `images`. Поле можна повторити — за раз
завантажується кілька файлів, і фото з відео можна змішувати в одному запиті.
Назва поля лишилася `images` заради сумісності зі старим клієнтом.

Тип визначається за **вмістом файлу**, а не за розширенням: файл, що починається
сигнатурою MP4/MOV (`ftyp`), іде у відеогілку, решта — в обробку як зображення.
Тож кліп, надісланий під іменем `clip.bin`, усе одно буде розпізнано.

### Що відбувається з фото

1. Застосовується орієнтація з EXIF.
2. Центральний кадр під пропорцію панелі та зменшення до **600×1024**.
3. Мініатюра 180×307 у `.thumbnails/`.
4. Ім'я перебудовується на `<мітка-часу-мс>_<очищена-назва>.jpg`.

Вертикальне фото зберігає всю висоту — підрізаються боки. Горизонтальне втратить
краї: панель вертикальна, і вмістити його без обрізки неможливо.

### Що відбувається з відео

1. Файл перевіряється через `ffprobe` — див. [вимоги](#яке-відео-рамка-може-показати).
2. Якщо рамка його не подужає, файл **видаляється з диска**, а причина приходить
   у `data.rejected`.
3. З кліпу береться кадр приблизно на першій секунді (не з нульової: кліпи надто
   часто починаються з чорного) і стає мініатюрою 180×307.
4. Ім'я перебудовується на `<мітка-часу-мс>_<очищена-назва>.mp4`.

Відео **не перекодовується і не кадрується**. Одне ядро 700 МГц витратило б на це
хвилини, тож файл має приїхати вже готовим — [рецепт](#рецепт-перекодування) нижче.

### Відповідь

```json
{
  "success": true,
  "message": null,
  "data": {
    "images": ["1788678129302_photo.jpg", "1788678131044_clip.mp4"],
    "rejected": []
  }
}
```

У `data.images` — **імена, під якими файли збережено**. Вони не збігаються з
надісланими, тож клієнт має зберігати саме ці значення.

`data.rejected` — **нове поле**: усе, що не взяли, з причиною на кожен файл.

```json
{
  "success": true,
  "message": null,
  "data": {
    "images": ["1788678129302_photo.jpg"],
    "rejected": [
      { "name": "IMG_4410.MOV", "reason": "video is HEVC (H.265); the frame only plays H.264" }
    ]
  }
}
```

`success` тут лишається `true` — частина партії таки пройшла; він стає `false`,
лише коли не пройшло нічого. Раніше нечитабельні файли зникали мовчки, і клієнт
міг хіба що звірити кількість імен із кількістю надісланих файлів. Тепер причину
видно, і саме її варто показати користувачеві — надто для відео, де «не підійшло»
майже завжди означає конкретне «це HEVC».

### Помилки

| `message` | Коли |
|---|---|
| `Images is required` | у запиті немає поля `images` |
| `Images can not be processed` | не пройшов **жоден** файл; причини — в `data.rejected` |
| `Upload is larger than the frame accepts` | тіло запиту більше за `MAX_UPLOAD_MB` (дефолт 256 МБ) |

```bash
curl -H "Authorization: $KEY" \
  -F "images=@photo1.jpg" -F "images=@clip.mp4" \
  http://192.168.0.146:5000/api/v1/upload-images
```

> Обробка фото 3024×4032 займає близько **3 секунд**. Відео не перекодовується,
> тож витрати на нього — це запис файлу плюс `ffprobe` і один кадр на мініатюру.
> Ліміт часу на запит — 300 с, але клієнту варто ставити таймаут із запасом:
> вузьке місце — швидкість, з якою файл доїде по мережі.

## Яке відео рамка може показати

Найважливіший розділ для того, хто готує файли. Показ робить GPU через
`omxplayer`, і його можливості вужчі, ніж очікується.

| Параметр | Вимога | Чому саме так |
|---|---|---|
| Кодек | **H.264, і тільки він** | HEVC-блока в BCM2835 немає взагалі; MPEG-2 і VC-1 вимкнені (`vcgencmd codec_enabled` → `disabled`) |
| Профіль | Baseline / Main / High | вище High апаратний декодер не бере |
| Рівень | до **4.2** | |
| Пікселі | `yuv420p`, 8 біт 4:2:0 | 10-бітне відео декодується в кашу |
| Контейнер | MP4: `.mp4`, `.m4v`, `.mov` | |
| Роздільність | до 1920×1088 | межа за замовчуванням; правильно — одразу 600×1024 |
| Тривалість | до 300 с | `MAX_VIDEO_SECONDS` |
| Розмір запиту | до 256 МБ | `MAX_UPLOAD_MB` |
| Звук | ігнорується | рамка програє без звуку; доріжку можна лишити — її не читатимуть |

> **iPhone за замовчуванням знімає в HEVC.** Такий файл рамка не покаже за жодних
> налаштувань. Це не обмеження коду, яке можна послабити, — у чипі немає
> відповідного блока.

Відео, що не пройшло перевірку, не зберігається: замість чорного прямокутника в
слайдшоу клієнт одразу отримує текст на кшталт
`video is HEVC (H.265); the frame only plays H.264` або
`H.264 level 5.1 is above the frame limit of 4.2`.

### Рецепт перекодування

Готуй файл під точний розмір панелі:

```bash
ffmpeg -i input.mov \
  -vf "scale=600:1024:force_original_aspect_ratio=increase,crop=600:1024" \
  -c:v libx264 -profile:v high -level 4.0 -pix_fmt yuv420p \
  -r 25 -b:v 2M -movflags +faststart -an \
  output.mp4
```

`crop` після `scale` дає той самий центральний кадр, який рамка робить для фото,
тож фото й відео в галереї виглядають однаково скадрованими. `-an` викидає звук,
`-movflags +faststart` кладе індекс на початок файлу — з ним `omxplayer` починає
показ, не вичитуючи весь файл.

## `POST /api/v1/delete-images`

Видаляє фото та їхні мініатюри.

**Тіло** — приймається у двох виглядах:

```json
{ "images": ["1744960595611_IMG_1611.jpeg"] }
```

або form-data з полем `images`, `images[]` чи індексованим `images[0]`, `images[1]`.
Одиничний рядок замість масиву в JSON теж приймається.

### Відповідь

```json
{ "success": true, "message": null, "data": { "images": ["1744960595611_IMG_1611.jpeg"] } }
```

`data.images` — **фактично видалені** імена. Якщо надіслати десять, а існують три,
у відповіді буде три, і `success` лишиться `true`.

### Помилки

| `message` | Коли |
|---|---|
| `Images is required` | список порожній або поля немає |
| `Images not found` | жодне з імен не знайдено на диску |

Імена перевіряються: приймається лише голе ім'я файлу. Значення зі слешами або
крапкою на початку (`../../etc/passwd`, `.thumbnails`) відкидаються — вийти за межі
теки галереї через цей метод неможливо.

```bash
curl -H "Authorization: $KEY" -H "Content-Type: application/json" \
  -d '{"images":["1744960595611_IMG_1611.jpeg"]}' \
  http://192.168.0.146:5000/api/v1/delete-images
```

## `POST /api/v1/restart-slideshow`

Каже рамці перечитати галерею негайно.

**Що змінилося.** Раніше показ робив `fbi`, який читав список файлів один раз, при
старті: без цього виклику нове фото на рамку не потрапляло взагалі, а сам виклик
тривав близько 7 секунд. Тепер плеєр перечитує теку **на кожному колі**, тож
завантажене чи видалене з'явиться і зникне саме, протягом одного слоту (60 с).

Виклик лишився і робить рівно одне: не змушує чекати цей слот. Тіла немає,
відповідь приходить **одразу** — це `SIGHUP`, а не перезапуск. Якщо плеєр чомусь
не запущений, виклик його підніме.

```json
{ "success": true, "message": null, "data": { "active": true, "state": "active" } }
```

При невдачі — `"success": false`, а в `message` буде вивід керуючого скрипта.

```bash
curl -X POST -H "Authorization: $KEY" \
  http://192.168.0.146:5000/api/v1/restart-slideshow
```

> Типовий сценарій клієнта: завантажити файли → отримати імена → викликати
> `restart-slideshow`. Один виклик після всієї партії, а не після кожного файлу.
> Тепер він **необов'язковий** — без нього рамка оновиться сама протягом хвилини, —
> але дешевий, тож лишати його в сценарії варто.

## `GET /api/v1/slideshow-status`

Показує, чи працює зараз плеєр.

```json
{ "success": true, "message": null, "data": { "active": true, "state": "active" } }
```

`active` — булеве значення для перевірки в коді; `state` — `active` або `inactive`.
`success` тут завжди `true`: сам факт, що слайдшоу стоїть, не є помилкою запиту,
тож дивитися треба на `data.active`.

```bash
curl -H "Authorization: $KEY" \
  http://192.168.0.146:5000/api/v1/slideshow-status
```

## Приклад клієнта (Laravel)

```php
use Illuminate\Support\Facades\Http;

$frame = Http::withHeaders(['Authorization' => config('services.frame.key')])
    ->baseUrl('http://192.168.0.146:5000/api/v1')
    ->timeout(300);

// Завантаження: фото й відео йдуть одним полем `images`
$response = $frame
    ->attach('images', file_get_contents($photo), 'photo.jpg')
    ->attach('images', file_get_contents($clip), 'clip.mp4')
    ->post('/upload-images')
    ->json();

if (! $response['success']) {
    throw new RuntimeException($response['message']);
}

$stored = $response['data']['images'];   // імена, під якими файли збережено

// Те, що рамка не взяла, з причиною на кожен файл — це варто показати користувачеві
foreach ($response['data']['rejected'] ?? [] as $item) {
    logger()->warning("Рамка відхилила {$item['name']}: {$item['reason']}");
}

// Показати нові фото на рамці
$frame->post('/restart-slideshow');

// Видалення
$frame->asJson()->post('/delete-images', ['images' => $stored]);
```

## Коротко

| Метод | Шлях | Призначення |
|---|---|---|
| `GET` | `/api/v1/list-images` | Сторінка галереї з мініатюрами; `type` — `image` або `video` |
| `POST` | `/api/v1/upload-images` | Завантажити фото і відео (multipart, поле `images`) |
| `POST` | `/api/v1/delete-images` | Видалити за іменами |
| `POST` | `/api/v1/restart-slideshow` | Оновити рамку негайно (інакше вона оновиться сама) |
| `GET` | `/api/v1/slideshow-status` | Чи працює слайдшоу |

Про саму рамку, її геометрію та автозапуск слайдшоу — див. [`deploy/README.md`](deploy/README.md).
